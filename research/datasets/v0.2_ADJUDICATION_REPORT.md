# TermAssist-Bench v0.2 — Adjudication Report

**Purpose:** targeted expansion of the OOD and AMBIGUOUS subsets, motivated directly by
Phase 17's decision gate — the OOD detection improvement (26.7%→46.7%) was large but not
statistically confirmed at n=15 (p=0.25, Phase 13). This is the single highest-leverage
benchmark improvement identified in `research/paper/PUBLICATION_ROADMAP.md`, grounded in
Card et al. (EMNLP 2020) on NLP benchmark statistical power.

**v0.1 is unmodified.** All 150 original queries and their files remain byte-identical. v0.2 is
a new, separate, frozen artifact (`termassist_bench_v0.2_validated.json/csv`), following the
exact same design/inclusion/exclusion criteria documented in `TERMASSIST_BENCH_DESIGN.md`.

## Provenance disclosure

The 59 new v0.2 queries (TA-B151–TA-B209) were authored and adjudicated by an AI agent (Claude),
under human direction, following v0.1's documented methodology. This is disclosed explicitly, not
hidden — v0.1's own queries were built the same way (`validation_audit.md`: "Audit report
generated autonomously"), so this is a continuation of the established process, not a new one.
**Adjudication was grounded in actual system behavior, not intuition alone**: every candidate was
run through the real BM25 (`lexical_search.js`) and dense (`dense_search.js`) retrieval used
throughout this research program, and accept/reject decisions were made from that output
(`research/datasets/v0.2_adjudication_raw.json`).

## Process (mirrors TERMASSIST_BENCH_DESIGN.md section 12)

1. **Draft**: 35 OOD candidates (diverse off-topic domains not overlapping the 15 existing OOD
   queries) and 30 ambiguous candidates (17 single-keyword, covering corpus categories not
   already used as bare-keyword ambiguous queries in v0.1, plus 13 multi-word phrasings).
2. **Verify against retrieval**: every candidate run through both BM25 and dense retrieval.
3. **Adjudicate**: accept only candidates meeting v0.1's definitions (section 7-8) — reject
   anything with one dominant, unambiguous answer (fails the ambiguity test) or anything
   near-duplicating an existing v0.1 query (exclusion criterion 5).
4. **Assign fields**: difficulty, risk_level, category, acceptable_commands — per the same
   criteria as v0.1.

## OOD candidates: 35/35 accepted

All 35 candidates verified genuinely out-of-domain: top lexical BM25 score never exceeds 7.39
(canonical in-domain matches score 40+; the substring bonus, +15.0, never fires on any of them),
and top dense cosine similarity never exceeds 0.31 (correct in-domain predictions average ~0.98).
Difficulty assigned by a stated, mechanical rule: `easy` if lexical score is exactly 0 AND dense
similarity < 0.20, else `hard` (8 easy / 27 hard) — several "hard" cases deliberately illustrate
incidental lexical/semantic overlap with an unrelated corpus command (e.g. "diagnose why my car
won't start" scores 5.55 against `Start-Service` purely from the word "start"), exactly the
"plausible terminal-adjacent, difficult to reject" category the original design calls for.

## Ambiguous candidates: 24/30 accepted, 6 rejected (rejections documented, not hidden)

**Accepted (24):** 17 single-keyword (`grep`, `tar`, `sed`, `awk`, `jq`, `ffmpeg`, `aws`, `disk`,
`system`, `shell`, `terminal`, `package`, `security`, `encoding`, `archive`, `pip`, `find`) and 7
multi-word (`stop a process`, `check disk usage`, `search for a file`, `list running processes`,
`check network connection`, `install a package`, `copy a file`) — each verified to have 2–3
genuinely distinct valid corpus interpretations, not just BM25 ties among near-identical
parameter variants of the same command.

**Rejected (6), with reasons:**
- `compress a folder` — one dominant, unambiguous answer (`Compress-Archive`); other candidates
  scored 0 or were irrelevant. Fails the ambiguity definition (section 7).
- `restart a service` — `Restart-Service` is the clear single answer; the next-highest scorer
  (`sudo reboot`) is a different task entirely (the whole machine, not "a service").
- `check git history` — near-duplicate of the existing v0.1 query "view the git log" (exclusion
  criterion 5).
- `extract an archive` — one dominant answer (`Expand-Archive`); alternatives were the opposite
  operation (compress) or a dry-run flag of the same command, not distinct valid interpretations.
- `convert a video file` — one clearest reading (transcode); redundant with the already-accepted
  bare-keyword `ffmpeg` case, which already tests ffmpeg-family ambiguity.
- `kill a process` — `Stop-Process -Id` and `-Name` are the same command with different
  parameters, not distinct tasks; the only genuinely different alternative (`tmux kill-session`)
  scored far below (4.94 vs 25.42/25.03), not a close ambiguous tie.

**A genuine, notable finding from this process:** the `tar` bare-keyword candidate initially
appeared to fail verification (its top lexical matches were unrelated docker/tmux/screen
commands, not any of the corpus's 5 actual tar commands). Investigation found the root cause:
`tar.gz` in those commands' intent text tokenizes into a single merged token (`targz`) under
`cli/search.js`'s punctuation-stripping tokenizer, so the literal token `tar` never appears in
most tar-related intents. This is a genuine tokenization-gap finding — accepted as an adversarial
ambiguous test case specifically because it exposes this, not despite it, and documented in the
query's own `notes` field rather than silently worked around.
